# P7.1 architecture issue handoff — live coordinate/schema conflict

**Status:** BLOCKED at L004 before any replacement result row was appended  
**Observed:** 2026-08-27 UTC  
**Audience:** architecture agent and operator  
**Issue ID:** `P7.1-L004-SCHEMA-01`

## 1. Executive summary

P7.1 requires every live isolated re-run coordinate to record
`resolved_by: live_heartbeat`. The unchanged results-row schema rejects that value: its coordinate enum permits only
`lsn_first`, `snapshot_first`, and `time_first`.

This is a normative conflict, not an operational outage. Continuing by extending the schema would violate the P7.1
clauses that explicitly leave it unchanged. Continuing by relabelling `live_heartbeat` as `lsn_first` would create a
plausible but false experimental record and fail L004 acceptance. An architecture amendment is required.

## 3. Normative conflict

Requirements mandating the new value:

1. `run-matrix-plan.amendment-1.md` A2 requires a live isolated cell to resolve and record
   `resolved_by: live_heartbeat` with measured skew.
2. `incident-isolation.md` section 7 requires the same and prohibits `snapshot_first` for a live re-run.
3. `WI-L004.md` L004-1 mechanically inspects re-run rows for `live_heartbeat` and non-zero measured skew.
4. `spec.md` FR-5 and AC-P7.1-10 repeat that requirement.

Requirements prohibiting the apparent fix:

1. `run-matrix-plan.amendment-1.md` A6 says the results-row schema is unchanged.
2. `incident-isolation.md` section 8 says the results-row schema is unchanged.
3. `etc/results-row.schema.json`, derived from the frozen P1 results-row contract, permits only
   `lsn_first | snapshot_first | time_first` for every coordinate object's `resolved_by` field.
4. `lib/generate_results_schema.py` generates that same three-value enum.

The first rejected field is `ground_truth_coordinate`; chosen and naive live coordinates would encounter the same
enum restriction.

## 5. Invalid workarounds rejected

- Do not label a live-heartbeat lookup `lsn_first`. That erases the isolation evidence and makes the row misleading.
- Do not put `live_heartbeat` only in free-form `validation_detail` while emitting another value in the coordinate.
  L004 requires the coordinate record itself and its mechanical acceptance test to carry the method.
- Do not silently edit the generated schema while A6 and section 8 say it is unchanged.
- Do not weaken the row validator or L004-1.
- Do not convert the rejection into a dropped cell. Article XIX requires retention and a validity partition.

## 6. Architecture decision required

Recommended resolution: issue a P7.1 amendment that explicitly authorizes the backward-compatible coordinate enum
extension `live_heartbeat`, updates the schema derivation source, and states its scope across
`ground_truth_coordinate`, `chosen_coordinate`, `naive_coordinate`, `incident_open_coordinate`, and
`incident_close_coordinate`. The amendment should also specify whether historical records remain valid without
migration (they should, because the extension is additive).

Alternative: define a different schema-compatible and semantically truthful representation of live resolution, then
update A2, section 7, FR-5, AC-P7.1-10, and WI-L004-1 consistently. No such representation currently exists in the
work package.

The architecture response must settle these questions:

1. Is the P1-derived results schema permitted to receive the additive enum value?
2. Which coordinate fields may carry `live_heartbeat`?
3. Is `live_heartbeat` a resolution-source value distinct from `lsn_first`/`time_first`, or should the model separate
   query direction from evidence source into two fields?
4. Which contract or amendment owns that semantic change and its new hash?
5. Which existing gates must accept and negatively test the new value?
