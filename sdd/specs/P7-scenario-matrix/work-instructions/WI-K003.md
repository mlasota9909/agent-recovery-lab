## Objective

Author SC-03: an agent runs a destructive migration in stages over time — dropping a column, altering a type, dropping
a constraint — while legitimate DML continues against the affected tables. Define the injector, the interleaved-DML
confounder, and the ground truth, and measure the single-coordinate trade-off honestly.

## Background (read before editing)

SC-03 changes the signal from *volume* (SC-01) to *pattern*: staged DDL, not a burst. It deliberately breaks the
single-clean-coordinate assumption — restoring to the LSN before the first destructive DDL also discards the
legitimate DML committed during the migration window. This is a `set_and_earliest`-flavoured scenario for reporting:
you compute the single-coordinate optimum AND the legitimate DML that a single-coordinate restore sacrifices. That
trade-off is the selective-recovery future-work hook; hiding it would misrepresent the result (ADR-P7-3, Article
XVIII spirit). DDL is invisible to logical decoding, so the `lab_ddl_audit` event trigger (ADR-007, P2) is what makes
DDL appear in the ledger — confirm DDL is flagged distinctly from DML. Corpus citation: destructive DDL / long-running
structural operations (Garcia-Molina & Salem, 1987).

## Steps

1. Write the SC-03 scenario definition: `damage_class=database_schema`, `timing_pattern=slow`,
   `corpus_citation=[GarciaMolinaSalem1987]`, `ground_truth.kind=set_and_earliest`, with metrics
   `single_coord_optimum_lsn`, `legit_dml_sacrificed`, `ddl_ops_retained`.
2. Injector (`scenarios/sc03/inject.sql`), as the agent principal: a sequence of destructive DDL (drop column, alter
   type, drop constraint) spread over time at recorded LSNs, with the DDL committed distinctly.
3. Confounder (`scenarios/sc03/workload.*`), as the app principal: normal reads/writes against the affected tables
   continuing during the staged migration, so legitimate DML is interleaved with the DDL (and any cascade side
   effects) throughout the window.
4. Oracle (`scenarios/sc03/oracle.*`): `single_coord_optimum_lsn` = the LSN before the first destructive DDL;
   `legit_dml_sacrificed` = the legitimate DML committed in the migration window that a restore to that LSN discards
   (computed from the reconciled ledger, provenance used for scoring only); `ddl_ops_retained` if restored later.
5. Generate one SC-03 incident end-to-end (T0), capture + reconcile (confirm DDL rows are flagged distinctly from DML
   via the `lab_ddl_audit` trigger), freeze it, record its `incident_id`. Do not touch SC-01.
6. Emit `logs/review/K003/sc03-tradeoff.json`: the single-coordinate optimum, the legitimate DML sacrificed at that
   coordinate, and the DDL-op count — all from committed fields.
7. Commit. Update the checklist row for K003.

## Negative test (required)

Construct a scratch SC-03 report that claims `legit_dml_sacrificed=0` while the reconciled ledger shows legitimate DML
committed in the migration window; assert the trade-off check, re-derived from the ledger, **catches** the false
zero and fails. Revert -> the sacrifice is computed truthfully. (This is the honest-reporting guard for SC-03.)
