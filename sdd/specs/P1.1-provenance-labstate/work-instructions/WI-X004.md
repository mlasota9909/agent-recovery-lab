## Objective

Turn "ready for P2" from a sentence in a memo into a mechanical, read-only gate, and provide a tested procedure to
restore readiness from the invalidated-slot state the lab is currently in.

## Background

The P1 end-state shows the replication slot with `invalidation_reason=wal_removed` and `slot_active=false`, consumer
unit disabled. P2's collectors attach to the logical-decoding stream, so P2 must not start from this state. The
correct repair for an invalidated slot is to roll back to a T1/T2 snapshot that still contains the slot — **not** to
create a new slot, which would desynchronise the slot from the append-only host ledger.

## Steps — the gate

1. Build `bin/lab-ready` (read-only; it must never mutate state). It resolves the open incident from
   `archive/current`, then checks and prints, as one JSON object, every one of:
   - `incident` — resolved from `archive/current`; failure if unresolvable;
   - `consumer_unit_state` — the `lab-consumer@<incident>` systemd unit is `active`;
   - `slot_active` — true in `pg_replication_slots`;
   - `invalidation_reason` — null;
   - `slot_check` — `bin/lab-slot --check` exits 0 and retention is below the warn threshold;
   - `db_jsonl_present` — the incident's `evidence/.../db.jsonl` exists;
   - `db_jsonl_growing` — its byte size increases across a short observation window (e.g. two reads ~2 s apart), or
     the confirmed_flush_lsn advances; state which signal you used;
   - `ready` — the AND of the above.
2. Exit 0 iff `ready` is true. On any failure, exit non-zero and set a `failed` array naming each unmet condition.
   Do not print private key material. Never call a model. Never write to victim state.
3. `bin/lab-ready` must discover all names/paths from `etc/lab.env`; no literals.

## Steps — the runbook

4. Write `docs/runbook-slot-recovery.md`: the exact, ordered procedure to restore readiness from an invalidated or
   inactive slot, using only existing CLIs:
   - stop PostgreSQL (required before reset);
   - `bin/lab-reset` to a T1 (`pre_injection`) or T2 (`post_capture`) snapshot that still contains the slot — state
     how to choose, and that a fresh slot must **not** be created;
   - start the consumer for the incident;
   - `bin/lab-barrier` until `bin/lab-slot --check` exits 0;
   - `bin/lab-ready` to confirm.
   The runbook must explicitly warn that rollback discards current victim state, and note this is acceptable now
   because the P1 incident is a quarantined stub-only null run.
5. Execute the runbook once against the live lab to move it from its current invalidated state to ready. Capture
   before/after `bin/lab-ready` output. If the lab is already ready when you start, induce the failure safely for the
   negative test (see below) and then restore — do not leave the lab unhealthy.

## Negative test (required)

Stop the consumer (or, if you can do so without a destructive reset, mark the slot inactive) to force an unhealthy
state. Assert `bin/lab-ready` exits non-zero and the `failed` array names the exact condition. Then run the runbook
and assert `bin/lab-ready` returns to exit 0 with `slot_name` unchanged from before — proving recovery did not
fabricate a new slot. A gate that cannot go red, or a recovery that silently swaps the slot, is a fail.

## Review bundle

Standard five, plus `ready-pass.json`, `ready-fail.json`, `runbook-run.log`.

## Operator review checklist

- [ ] `bin/lab-ready` is read-only and checks every listed condition
- [ ] It exits non-zero and names the failed condition when the consumer is down
- [ ] The runbook restores readiness by rollback, never by creating a slot
- [ ] `slot_name` is unchanged across the recovery
- [ ] The lab is left healthy (`lab-ready` exit 0) at task end
