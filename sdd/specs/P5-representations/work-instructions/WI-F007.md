# WI-F007 — The identical-interface parity test

## Objective

Prove, mechanically, that the query interface is **structurally identical** across R0, R1 and R2: same request
acceptance, same probe set, same response envelope and same per-probe `answer` schema — with only `content` and
`telemetry` differing. Build `bin/lab-repr-parity <incident>` that asserts this and fails loudly on any structural
divergence. This is the property that makes the P6 ablation clean.

## Background

If R2 could return a field R0 does not, a P6 result could be explained by the interface rather than the representation.
The parity test compares the *structure* of responses (field set, types, `answer` sub-schema) across representations,
while explicitly ignoring the two fields that are allowed to differ (`content`, `telemetry`).

## Steps

1. For each of the six probes, call `bin/lab-repr-query` for R0, R1 and R2 with identical params.
2. Normalise each response by removing the values of `content` and `telemetry` (keep their keys and types) and compare
   the resulting structural skeletons across the three representations: identical key set, identical types, identical
   `answer` sub-schema. Any difference is a failure naming the probe and the divergent field.
3. Assert the accepted request set is identical: every probe answerable by R0 is answerable by R1 and R2, and none
   exposes a probe the others do not.
4. Emit `logs/review/F007/parity.json` (`{probe_id, structural_match:true}` per probe) and a human-readable
   `parity.md`.

## Negative test (required)

In a scratch build of the R2 responder, add a distinguishing structural field to one probe's response (e.g.
`answer.graph_hint`); run parity; assert it fails and names R2 + the probe + the added field. Revert -> parity passes.
