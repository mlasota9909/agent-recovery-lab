# WI-C006 — `bin/lab-query`: no-ETL DuckDB view layer over the ledger

| **Phase** | C — Query layer and workload |

## Objective

Present the whole ledger as queryable DuckDB views bound directly to the files, with no import/ETL step, and prove the
view layer agrees with a plain line count of the source.

## Background

Per ADR-P2-2 DuckDB is a read-only lens, never the store of record. It binds views to the ledger files
(`read_json_auto`, `read_csv`) and runs SQL over them in place. If DuckDB and the files ever disagree, the files win —
so every view must be cross-checkable against a trivial line/`jq` count. The default views must **exclude the
`principal` provenance field** (Article II, contract §5).

## Steps

1. Build `bin/lab-query <incident> "<sql>"` that opens DuckDB and defines views over the incident ledger, minimally:
   - `db_changes` — `kind='change'` rows from `db.jsonl` (**without** `principal`);
   - `heartbeats` — `kind='heartbeat'` rows;
   - `snapshots` — `snapshots.json`;
   - `fs_diff` — `fs_diff.tsv`;
   - `fs_hashes` — `fs_hashes.tsv`.
   Then run the caller's SQL and print the result.
2. No import/copy step: the views read the files directly each invocation. Grep your own code to prove there is no
   `COPY`/`CREATE TABLE AS ... ` that materialises the ledger into a DuckDB file as the store of record. A rebuildable
   Parquet cache is allowed only if it is clearly derived and never read in preference to the raw files for counts.
3. The default `db_changes` view must not project `principal`. Provide a separate, explicitly-named scoring view (used
   only by the oracle/`lab-ledger-account` scoring path) if a principal-bearing view is needed — never the default.

## Acceptance tests

| ID | Tier | Command | Expected |
| --- | --- | --- | --- |
| C006-1 | M | `bin/lab-query <inc> "select count(*) from db_changes"` vs `grep -c '"kind":"change"' db.jsonl` | equal (AC-P2-10) |
| C006-2 | M | inspect the code path for an ETL/import of the ledger as store of record | none; views read files in place |
| C006-3 | M | `bin/lab-query <inc> "select * from db_changes limit 1"` | no `principal` column present |
| C006-4 | M | query `snapshots`, `fs_diff`, `fs_hashes`, `heartbeats` | each returns rows matching the source files |

## Negative test (required)

Append one extra change line directly to a scratch copy of `db.jsonl`, point `lab-query` at the scratch ledger, and
assert the DuckDB count increases by exactly one and still equals the plain line count — proving the view reflects the
file rather than a stale materialisation. Then, separately, add `principal` to the default view and assert C006-3
fails; revert. A view layer that can silently diverge from the files, or that exposes `principal` by default, is a
fail.
