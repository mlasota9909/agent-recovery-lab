# WI-C003 — Snapshot loop LSN anchoring → `snapshots.json`

| --- | --- |

## Objective

Ensure every ZFS snapshot the capture loop takes is anchored to a WAL LSN, so a chosen database coordinate resolves
to a filesystem snapshot across layers (ADR-008).

## Background

`snapshots.json` must contain `{snapshot, wall_clock, lsn}` per snapshot. A snapshot with a null LSN is useless for
cross-layer recovery, so a missing LSN is a hard failure, not a warning. The loop takes a recursive snapshot of the
victim dataset every N seconds (N from `etc/lab.env`) and records the WAL position captured with `pg_switch_wal()`
(which also bounds the WAL segment so the coordinate is unambiguous).

## Steps

1. In the snapshot loop launched by `lab-capture`, for each tick:
   - call `pg_switch_wal()` (or `pg_current_wal_lsn()` if a switch is undesirable mid-transaction — state which and
     why) and capture the LSN;
   - take `zfs snapshot -r <victim-dataset>@<name>` with a monotonic name;
   - append `{ "snapshot": "<name>", "wall_clock": "<ISO-8601>", "lsn": "<X/Y>" }` to `snapshots.json`.
2. LSN strings are compared as integers `(high << 32) + low` everywhere downstream — record the recorded form so C008
   can parse it.
3. Idempotence/interval: the loop must not double-snapshot within a tick; interval and dataset come from `lab.env`.

## Acceptance tests

| ID | Tier | Command | Expected |
| --- | --- | --- | --- |
| C003-1 | M | run a capture window long enough for ≥2 snapshots; inspect `snapshots.json` | ≥2 entries, each with a non-null `lsn`, a `snapshot` name and a `wall_clock` (AC-P2-05) |
| C003-2 | M | `jq '.[] | select(.lsn==null)' snapshots.json` | empty (no null LSN) |
| C003-3 | M | verify LSNs are non-decreasing across snapshot order using integer comparison | monotonic |
| C003-4 | M | confirm each named snapshot exists in `zfs list -t snapshot` | all present |

## Negative test (required)

Temporarily patch the loop to record a snapshot without capturing the LSN (null), run one tick, and assert the C003-2
scan (and `lab-ledger-account` later) flags the null LSN as a failure. Revert and confirm the scan passes. A snapshot
record that can carry a null LSN silently is a fail.

## Review bundle

Standard five, plus `snapshots.json`, `lsn-null-scan.log`.

## Operator review checklist

- [ ] Every `snapshots.json` entry has a non-null LSN
- [ ] LSNs are monotonic under integer comparison, not string comparison
- [ ] Each named snapshot actually exists in ZFS
- [ ] The null-LSN negative test was caught, then passed after revert
