## Objective

Produce one real, reconciled SC-01 incident for the rest of P3 to analyse: a destructive bulk DB record deletion
(near-instant) injected as `lab_agent`, running concurrently with legitimate `lab_app` activity that **repeats keys**
(so the P2.1 concurrency regime is exercised), with the oracle parameters that make the SC-01 ground-truth optimum
computable. Bounded to SC-01 only (ADR-P3-6).

## Background

SC-01 is the vertical-slice scenario from the scenario pages: near-instant destructive deletion. P2 deliberately used
a generic workload, so no scenario injector exists yet. D002 reuses the P1 `generate-incident` harness (reset →
baseline → workload start → `pre_injection` snapshot → inject → capture stop → `post_capture` snapshot → register
incident id) and P2 capture; it adds only the SC-01 injector, the SC-01 workload profile and the oracle params. The
injector runs as the `lab_agent` principal so provenance labels it as damage for the oracle — but nothing in P3
detection reads that label (Article II).

## Steps

1. Build `bin/lab-inject-sc01 <incident>`: as the `lab_agent` Postgres role, perform a destructive bulk `DELETE`
   against the scenario relation(s) defined in the scenario config, near-instant (single burst). Write
   `injection_log.json` with the exact ops, affected natural keys, and the wall-clock/LSN damage window
   `[t_start,t_end]`/`[lsn_start,lsn_end]`. It must run only inside the lab (guard on `lab.env` markers) and must
   refuse to run against anything but the configured scenario relations.
2. Define the SC-01 concurrent legitimate workload profile driving `bin/lab-capture-workload` (or a thin SC-01
   wrapper) as `lab_app`: INSERT/UPDATE/DELETE with **repeated keys** (same row updated more than once; delete of an
   earlier-inserted row) so the reconciliation runs in the regime P2.1 made sound. Deterministic and seedable.
3. Declare the quiescent baseline window (a window before injection) and the SC-01 oracle parameters in scenario
   config, so D004 can score anomalies against a fixed baseline and P1's oracle can compute the true optimum.
4. Generate the incident end to end with the P1 harness, then run `bin/lab-ledger-account <incident>` and capture
   `ops`, `mapped`, `gaps=0`, `duplicates=0`, exit 0. Record the incident id (this is the incident D003+ analyse).

## Negative test (required)

Regenerate the SC-01 incident with `REPLICA IDENTITY DEFAULT` on a scenario relation (or with the consumer briefly
stopped mid-workload), then run `bin/lab-ledger-account`; assert reconciliation FAILs (missing before-image or a
coverage gap) and exits non-zero. Restore the correct configuration and confirm it reconciles exactly-once again. An
SC-01 incident that reconciles green under a broken capture config is a fail.
