## Objective

Prove the `xid`-keyed mapping is a correct bijection under the repeated-key concurrency the experiment actually runs
in, and — the load-bearing part — prove it **detects** a co-occurring gap+duplicate on a shared key that a count-only
check would report as clean. This is the direct evidence that certifying a ledger "complete" means something once
scenarios repeat keys.

## Background (read before editing)

The C007 acceptance workload uses globally-unique natural keys, so it cannot exercise the defect this tranche fixes.
Real scenarios (P3+) update the same row more than once and delete rows inserted earlier in the same incident, so
natural keys recur. The danger is a mapping that balances counts while pairing the wrong op to the wrong record. With
`xid` in the key, two operations on the same natural key in different transactions are distinguishable; two operations
on the same key in the **same** transaction are distinguishable by `action` and tuple identity. Y003 constructs both
and proves the mapping holds.

## Steps

1. Confirm `bin/lab-ready` exit 0; recover per runbook if needed; wait on `bin/lab-barrier` after any reset.
2. Add a **repeated-key workload profile** to `bin/lab-capture-workload` (or a thin wrapper the test drives): a small,
   deterministic sequence over a handful of natural keys that includes, at minimum — the same key updated twice in
   separate transactions; the same key updated twice within one transaction; a delete-then-reinsert of one primary
   key; and interleaved `lab_app` and `lab_agent` activity on shared keys (provenance recorded for scoring only). The
   sequence must be seeded and reproducible.
3. Capture one incident under this profile with the corrected consumer; confirm every ledgerable record carries `xid`.
4. **Positive reconciliation.** Run `bin/lab-ledger-account`; assert a clean bijection: every workload op mapped
   exactly once, gaps=0, duplicates=0, exit 0.
5. **Negative — the masked corruption.** Construct the co-occurring fault on a **shared** natural key: in a working
   copy of the incident's `db.jsonl`, **remove** the ledger record for one operation on that key and **duplicate** the
   ledger record for another operation on the same key, so the record count is unchanged. Re-run reconciliation.
   Assert it reports **gaps ≥ 1 and duplicates ≥ 1** and exits non-zero — i.e. the corruption is detected, not masked.
6. Record, for contrast, what a count-only check would have reported on the same corrupted ledger (equal counts →
   "clean"), to make explicit why the `xid`-keyed bijection is required. This contrast is evidence, not a second code
   path.
7. **Revert.** Restore the unmodified `db.jsonl`; re-run reconciliation; assert clean again (gaps=0, duplicates=0).
8. Do not modify any frozen contract, `bin/lab-ledger-account`'s key (owned by Y002), or the results row.

## Negative test (required)

The negative case **is** the point of this task (Y003-3), so it is mandatory and first-class: the injected
gap+duplicate must be caught. In addition, prove the test cannot silently pass without exercising the fault: comment
out the fault-injection step and assert `tests/reconcile-repeated-key.sh` reports that its negative phase did not run
(fails closed), rather than reporting overall PASS. Restore and confirm the full test passes.
