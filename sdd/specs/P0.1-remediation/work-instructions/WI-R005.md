## Objective

Prove that `bin/lab-reset --tier t1` refuses to roll back `DS_PGDATA` while PostgreSQL is live, that no rollback
occurs when it refuses, and that the same rollback succeeds once the cluster is stopped.

## The defect, precisely

T012 documented this guard and intended to test it. The test was **skipped**: guest `/tmp` is mounted `noexec`, so the
dropped test binary would not execute, and the case was recorded as not run. The guard is therefore undocumented by
evidence.

This matters more than a typical untested branch, for a specific reason: T012 is the same task that discovered a real
and subtle defect — `zfs rollback -r` on a parent dataset does **not** restore the contents of descendant datasets,
which required deepest-first child rollback to fix. A component that was one careful reading away from silently
corrupting every reset deserves its remaining safety guard proven rather than assumed.

The consequence if the guard is absent: rolling a data directory out from under a running cluster produces corruption
that can look like an experimental result rather than an infrastructure failure. That is the worst class of bug in this
project.

## Why `noexec` is not an obstacle

You do not need to execute a dropped file to hold a live process against a dataset. Three permitted mechanisms, in
order of preference:

1. **Use the cluster itself.** PostgreSQL is already a live process with open descriptors inside `DS_PGDATA`. If the
   guard's check is "is the cluster running", this is both the simplest and the most faithful test.
2. **Hold an open descriptor from a shell redirection.** `exec 9<some-file-inside-pgdata` in a shell that then sleeps.
   No executable file is created, so `noexec` is irrelevant.
3. **Run an interpreter already on an exec-permitted path**, for example `/usr/bin/sleep` or `python3 -c`, with its
   working directory or an open file inside the dataset.

Do not remount `/tmp`, do not disable `noexec`, and do not place a test binary elsewhere to work around it. The
environment is a fact to work with, not an obstacle to remove.

## Steps

1. Read `bin/lab-reset` and record precisely what the guard checks — cluster running, dataset busy, open descriptors,
   or something else. Test the guard as implemented, not as imagined. If the implementation differs from the
   documentation, that is a finding: record it and test both what it does and what it should do.
2. **Refusal case.** With PostgreSQL running, capture the current snapshot state of `DS_PGDATA` (snapshot list plus a
   content fingerprint — a recursive hash or a `zfs get` of the relevant properties). Run
   `bin/lab-reset --tier t1 <incident>`. Assert:
   - exit code non-zero;
   - the message names the precondition (cluster is live) and the remedy (stop it first);
   - **no rollback occurred** — the snapshot list and content fingerprint are byte-identical to the pre-attempt
     capture. This second assertion is the important one. A guard that refuses *after* rolling back is worse than no
     guard.
3. **Success case.** Stop PostgreSQL cleanly. Re-run the same command. Assert exit 0, and assert the rollback actually
   restored the expected state — confirm both the `pgdata` and `protected` children were restored, since this is where
   the descendant-rollback subtlety lives. Restart the cluster and confirm health.
4. **Descriptor case (if the guard checks descriptors rather than the service).** Repeat step 2 using mechanism 2, with
   the cluster stopped but an open descriptor held inside the dataset, and confirm the guard still refuses.
5. Add the test to the repository as a script so it is repeatable, and register it in `bin/lab-verify` as a tier M
   criterion (coordinate with R004 if run after it; if run before, note the registration as a handoff in
   `observations.md`).

## Negative test (required)

**N-1, the guard test can fail.** Temporarily neutralise the guard in a working copy — for example invert its
condition — and confirm `bin/lab-reset-guard-test` goes red on the refusal case. Restore the original guard, confirm
green. Do not leave the neutralised version anywhere in the tree, and assert its absence.

This is the point of the task: an untested guard and a guard with an untestable test are the same thing.

## Non-regression (required)

- The deepest-first child rollback behaviour from T012 is unchanged. Prove it: the success case must restore both
  children, which is exactly what a naive `zfs rollback -r` on the parent would fail to do.
- T1 reset still leaves host-side evidence byte-identical (the property the ablation depends on). Re-assert it.
- The cluster starts healthy after the success case, with no errors in the PostgreSQL log.

- [ ] Success case restores both `pgdata` and `protected`
- [ ] Cluster starts clean afterwards
- [ ] No `noexec` workaround; no remount; no binary dropped
- [ ] N-1 shows the test going red when the guard is neutralised
- [ ] Neutralised copy provably absent from the tree
