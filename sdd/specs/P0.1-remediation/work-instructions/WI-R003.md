# WI-R003 — Supervised decoding consumer; incident precondition; slot lag fails closed

| | |
| --- | --- |
| **Task** | R003 |
| **Phase** | C — Evidence continuity |
| **Depends on** | R001 |
| **Blocks** | R004, R007 |
| **Serves** | FR-3; RC-8 through RC-12 |
| **Est.** | 2–3 h |

## Objective

Stop the logical decoding slot from accumulating WAL toward invalidation, by running a persistent supervised consumer
that writes decoded change records into the evidence store, and by making slot lag a failing condition rather than an
observation.

## The defect, precisely

At P0 close the slot reported `active=false` with `retained_bytes = 436,278,992` against a 64 MiB warning threshold
and an 8 GB `max_slot_wal_keep_size`. AC-10 passed because it asserts only that retention is *bounded*. Boundedness
holds right up to the moment the cap is reached, at which point PostgreSQL invalidates the slot and the logical
decoding stream — the sole source of database change evidence — stops permanently until the slot is recreated.

The failure mode that matters: this happens partway through an unattended experimental matrix, hours in, and the loss
is not obvious. Runs after that point have filesystem evidence and no database evidence. If it goes unnoticed the
results are silently wrong, which is worse than a crash.

There is also a design gap behind it. P0 created the slot but never created a consumer, because consuming is P2's job.
The slot was therefore always going to grow. The fix is to bring the consumer forward, because the substrate is not
safe to leave running without it.

## Steps

### Part 1 — the consumer

1. Write `bin/lab-consumer` with subcommands `start <incident>`, `stop <incident>`, `status <incident>`, `position
   <incident>`. It wraps `pg_recvlogical` and nothing more. Article V: no bespoke daemon, no queue, no framework.
2. The consumer runs **on the host** (ADR-P01-4), connecting to the guest's PostgreSQL over the existing pull-based
   path. This keeps the victim's outward surface at exactly one narrow append channel, so ADR-002's isolation argument
   is unchanged. Do not run the consumer inside the VM.
3. Output goes to `<evidence>/<scenario>/<incident>/db.jsonl`, newline-delimited JSON, one decoded change per line,
   opened in append mode. Do not transform, filter, enrich or reorder records. Capture is capture; interpretation is
   P2's job.
4. `position` reports the last confirmed flush LSN, read from `pg_replication_slots.confirmed_flush_lsn`, so a restart
   can be reasoned about and any gap detected.
5. Write `etc/systemd/lab-consumer@.service` — a templated host unit, instantiated per incident, with
   `Restart=always`, a short `RestartSec` (2–5 s), and `StandardError` journalled. Install it host-side. Article V
   permits systemd because it is the platform's own supervisor, not a service framework you wrote.

### Part 2 — incident precondition

6. Modify `bin/lab-incident` so that `open` refuses, non-zero, when the consumer for the incident is not running and
   healthy. The message must name the precondition and the remedy.
7. Rationale to record in the code comment: an incident captured with no consumer is an incident with no database
   evidence. It must fail at open, loudly, rather than be discovered at analysis time when the runs are already spent.
8. `close`/teardown stops the consumer and records the final flush position into the incident's metadata.

### Part 3 — slot lag fails closed

9. Modify `bin/lab-slot --check` to exit **non-zero** on each of three conditions, where it previously warned:
   - retained WAL above the warning threshold from `lab.env`;
   - slot `active=false` while an incident is open;
   - slot in an invalidated state (`conflicting` / `invalidation_reason` non-null, per the server version's column).
10. Keep the threshold configurable in `etc/lab.env`. The failure message must name which condition tripped, the
    observed value, the threshold, and the remedy.
11. Measure steady-state retained WAL with the consumer running under the steady-state workload, and record the
    observed value into `etc/lab.env` as a new key. This is the number that proves the fix worked, and it belongs in
    the recorded results.

## Negative test (required)

**N-1, the old defect can no longer pass.** Reproduce the P0 condition deliberately: stop the consumer, drive WAL
generation until retention exceeds the warning threshold, and run `bin/lab-slot --check`. Under P0 this returned 0
with a warning. It must now return non-zero. Capture both the observed retained bytes and the exit code. This is the
single most important artefact in the task.

**N-2, restart does not silently lose records.** Note the line count and last flush position, `kill -9` the consumer,
write a known number of additional rows, wait for restart, and confirm the decoded stream contains those rows. If
there is a gap, record it precisely — a measured gap is a finding worth reporting, an unmeasured one is a defect.

## Non-regression (required)

- Existing archiving and PITR configuration untouched: confirm `archive_command` and `wal_level` unchanged from their
  P0 values.
- The `wal2json` slot is the same slot, not recreated: record its name and creation state before and after.
- Heartbeat writer from T010 still running and unaffected.
- `bin/lab-isolation-test` still passes, including R002's enumeration corpus — the consumer must not have introduced
  any new inward path.

## Review bundle

Standard seven, plus `slot-before-after.json` (retained bytes and active state before and after the consumer),
`restart-continuity.md` (N-2 evidence with the line counts and positions), `unit-file.txt`, and `steady-state.md`
recording the measured retention with the workload running.
