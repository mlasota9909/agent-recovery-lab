## Objective

Remove the stale pre-migration PostgreSQL data directory left on the guest, and pin the exact environment versions
into a machine-readable artefact so the environment table is generated rather than hand-typed.

## Why both halves matter

**The stale directory.** `${PG_DATA}.pre-zfs` is a complete copy of a PostgreSQL data directory from before the T003
migration onto ZFS. Two risks: a later restore path or a human could mistake it for live data, and it consumes space
on the dataset that experimental runs need. It served its purpose as a migration safety net and T003's bundle has been
reviewed, so it should go.

**The versions.** Reproducibility is a claim the experiment makes. A reader who cannot tell which PostgreSQL minor version
produced the decoded stream cannot reproduce the work. The P0 build recorded Ubuntu 26.04 and PostgreSQL 18.4 in
free text; that is not reproducible and not machine-readable. Generate the table from `lab.env` so it cannot drift from reality.

## Steps

### Part 1 — remove the stale directory

1. **Before deleting anything**, assert all of the following and record each:
   - the live PostgreSQL data directory resolves to a path on `DS_PGDATA` (confirm via `SHOW data_directory` against
     the running cluster, and via `zfs list`/mount output — two independent sources);
   - the cluster is running and healthy;
   - a trivial write-and-read round trip succeeds;
   - `${PG_DATA}.pre-zfs` is **not** the live directory and is not referenced by any config file, unit or script under
     the deploy root (grep for it).
2. Record the stale directory's size and a listing of its top level, for the record.
3. Remove it. If any assertion in step 1 fails, stop and report; do not delete.
4. Re-assert cluster health after removal, and re-run a write-and-read round trip.

### Part 2 — pin versions

5. Discover and record into `etc/lab.env`, as new flat keys: guest OS release (distribution and version), guest kernel
   release, ZFS kernel-module version and ZFS userland version, PostgreSQL server version (full, including minor),
   `wal2json` extension version, host OS release, host kernel release. Also record the observed device paths and
   `DEV_LOCATION` if not already present.
6. Discover, never assume. Each value comes from a command whose output you capture. No placeholders.
7. Do not change the meaning of any existing `lab.env` key — Article VII. Adding keys is permitted here because FR-6.2
   requires it; redefining an existing key is not.

### Part 3 — generate the environment table

8. Write `bin/lab-environment`, which reads `etc/lab.env` and emits a markdown table to stdout: component, version,
   source of the value. It must be generated on demand, never hand-edited.
9. Write its output to `docs/environment.md` with a generated-file header naming the generating command and the
   generation timestamp.
10. Confirm the generated table contains no placeholder, no `unknown`, and no empty cell. An empty cell means a
    discovery step failed silently, which is an Article VIII violation.

## Negative test (required)

**N-1, the generator fails loud on a missing value.** Temporarily remove one pinned key from `etc/lab.env`, run
`bin/lab-environment`, and confirm it exits non-zero naming the missing key rather than emitting an empty cell or the
word `unknown`. Restore the key and confirm the table regenerates identically.

This matters because a silently empty environment table is exactly the kind of defect that reaches the results unnoticed.

## Non-regression (required)

- Cluster starts, runs and serves reads and writes after the removal.
- Every pre-existing `lab.env` key retains its original value and meaning; produce a before/after key diff showing
  only additions.
- `bin/lab-verify` still passes (whatever the current tier state — if R004 has not yet run, note it).

## Review bundle

Standard seven, plus `pre-zfs-listing.txt`, `version-discovery.log` (each value with the command that produced it),
`lab.env.keydiff.md` (additions only), and the generated `docs/environment.md`.
