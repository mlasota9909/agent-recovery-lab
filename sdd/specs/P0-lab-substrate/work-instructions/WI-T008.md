## Objective

Create the two lab identities at both OS and database level, so that legitimate and damaging activity are
distinguishable in the evidence by recorded principal — replacing the containers we deliberately rejected (D-8).

## The rule that makes or breaks the experiment

Constitution **Article II**: provenance exists **for scoring only**. The ground-truth oracle may read it; the analysis
engine, the representation builders and any model may **never** read it. If a detector can see which principal made a
change, it has been handed the answer key and every result is worthless.

T008 creates the field. T003-era analytics do not exist yet. **P3 enforces the negative test** (strip provenance from
the analytics view, assert the selected coordinate is unchanged). Write this forward-reference into
`observations.md` so it is not forgotten.

## Steps

1. Create OS users `lab_app` and `lab_agent` in the guest, no sudo, no shared group with `postgres`, separate home
   directories, mode 0700.
2. Create database roles `lab_app` and `lab_agent` with `LOGIN`, distinct passwords stored only in the guest users'
   own `~/.pgpass` (mode 0600). Do not print passwords into any log or review bundle.
3. Grant `lab_app`: `SELECT`, `INSERT`, `UPDATE` on `lab_ledger` and `lab_reference`, and usage on sequences. This is
   the steady-state legitimate workload's ceiling.
4. Grant `lab_agent` exactly what the four scenarios require and nothing more:
   - SC-01 mass delete -> `DELETE` on `lab_ledger`
   - SC-02 filesystem damage -> OS write access to `MNT_PROTECTED` only
   - SC-03 schema damage -> ability to `ALTER`/`DROP` the scenario relations
   - SC-04 stealthy corruption -> `UPDATE` on `lab_ledger`
   Grant no superuser, no replication, no access to `lab_ddl_audit` contents, no access to `lab_heartbeat` writes.
5. Confirm the `SECURITY DEFINER` DDL audit path works for `lab_agent`: it can *cause* audit rows by running DDL, and
   cannot `SELECT`, `UPDATE` or `DELETE` from `lab_ddl_audit`.
6. Ensure provenance is recoverable from the decoded stream. `wal2json` does not necessarily carry the role on every
   record, so establish the mapping explicitly and record how: for example, one dedicated connection/session per
   principal with a recorded session start, or a lightweight per-principal marker table written at session open. State
   the chosen mechanism precisely — this is what the oracle relies on.
7. Verify `MNT_PROTECTED` permissions: `lab_agent` can damage files there; `lab_app` writes only its own subtree.
8. Record `ROLE_APP`, `ROLE_AGENT`, `OS_USER_APP`, `OS_USER_AGENT` in `lab.env`.

## Acceptance tests

| ID | Command | Expected |
| --- | --- | --- |
| T008-1 | `id lab_app; id lab_agent` | both exist, no sudo group |
| T008-2 | `\du` | both roles present, neither superuser nor replication |
| T008-3 | as `lab_agent`: `DELETE FROM lab_ledger WHERE id=<one>` | succeeds |
| T008-4 | as `lab_agent`: `SELECT * FROM lab_ddl_audit LIMIT 1` | permission denied |
| T008-5 | as `lab_agent`: `CREATE TABLE zz(x int)` then as `postgres` read audit | audit row exists with `principal=lab_agent` |
| T008-6 | as `lab_app`: `DELETE FROM lab_ledger` | permission denied |
| T008-7 | one change by each principal, decoded | the two are distinguishable by recorded provenance (AC-11) |
| T008-8 | `sudo -u lab_app touch $MNT_PROTECTED/../escape` | denied |
| T008-9 | re-run task script | `"changed": false` |

## Negative test (required)

Grant `lab_app` the `DELETE` privilege, show T008-6 now *passes* (i.e. the least-privilege assertion fails), then
revoke and show it failing again. This proves the privilege assertions are real. Capture both. Do not leave the extra
grant in place.

## Review bundle

Standard five, plus `grants.sql` (exact grants applied), `provenance-mechanism.md` (how principal is recovered from
the stream, and why it is reliable), `least-privilege-matrix.md`, `negative-test.log`. **No passwords anywhere.**
