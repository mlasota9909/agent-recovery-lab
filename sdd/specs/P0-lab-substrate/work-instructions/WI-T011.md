## Objective

Implement the coordinate triple from `contracts/coordinate.md`: take recursive snapshots that record their LSN, force a
WAL switch at each, and resolve any of `--lsn` / `--time` / `--snapshot` into a full coordinate with **measured skew**.

## This is the task that dissolves the hardest integration problem

Rudri flagged that reconciling filesystem and WAL evidence into one view was named but unsolved. The resolution is not
to eliminate skew — that is impossible, since the database can restore to any LSN but the filesystem only to a snapshot
boundary. It is to **anchor the two and report the residual skew as a measured quantity per run** (D-6). Skew becomes a
result, not a defect.

## Steps

1. `bin/lab-snapshot`:
   - takes `zfs snapshot -r $DS_PARENT@${SNAP_PREFIX}<UTC timestamp>`,
   - immediately records `pg_current_wal_lsn()`,
   - calls `pg_switch_wal()` so the segment containing that position is archived promptly,
   - appends a record to the incident's `snapshots.json`: snapshot name, creation time, recorded LSN, and the order of
     operations actually used,
   - prints the record as JSON.
   Accept `--label pristine|pre_injection|post_capture|<free>` so reset targets are nameable.
2. **Ordering matters and must be stated.** Record LSN as close as possible to the snapshot instant and document
   whether LSN was read immediately before or after the snapshot, since that determines the sign of the residual skew.
   Do not leave it implicit.
3. `bin/lab-snapshots` lists snapshots with recorded LSN and label as a JSON array.
4. `bin/lab-coordinate` implements the contract's resolution rules exactly:
   - `--lsn X/Y` -> newest snapshot **at or below** that LSN;
   - `--time <iso>` -> newest heartbeat at or below, then rule 1;
   - `--snapshot <name>` -> that snapshot's LSN, skew zero;
   - always compute and emit `skew_ms` and `skew_bytes`;
   - never round skew away, never default it to zero;
   - fail non-zero if no snapshot at or below exists — no falling back to the oldest.
5. Implement the **heartbeat-gap rule** passed forward from T010: if `--time` falls in a window with no heartbeat
   within a stated tolerance, emit a `degraded` flag and a `gap_ms` field rather than interpolating. Fabricating a
   coordinate across a gap would be an Article VIII violation.
6. `skew_bytes` is a WAL-position difference; compute it with `pg_lsn` arithmetic, not by parsing strings.
7. Record `SNAP_PREFIX`, `SNAP_PRISTINE`, `SNAP_PRE_INJECTION`, `SNAP_POST_CAPTURE` in `lab.env`.

## Negative test (required)

Construct a case where a snapshot exists **above** the target LSN and assert the resolver does **not** select it —
selecting a later snapshot would return state that already contains the damage, which is the single most dangerous
possible bug in this system. Capture the assertion. Also confirm skew is never silently zeroed by testing an LSN
deliberately far from any snapshot.

## Review bundle

Standard five, plus `snapshots.json` sample, `coordinate-cases.json` (one entry per acceptance case with the observed
output), `ordering-decision.md` (LSN before or after snapshot, and the skew-sign consequence),
`negative-above-lsn.log`.

## Operator review checklist

- [ ] Snapshot records LSN **and** forces a WAL switch
- [ ] Resolver never picks a snapshot above the target LSN
- [ ] Skew reported in both ms and bytes, never suppressed
- [ ] Heartbeat gaps produce `degraded`, not interpolation
- [ ] Output validates against the frozen contract
