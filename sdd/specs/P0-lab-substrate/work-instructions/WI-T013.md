## Objective

Prove that filesystem change evidence and past filesystem content are both obtainable from stock ZFS facilities, with
**no** event daemon, clone, loop mount or `zfs send` anywhere (Article V).

## What this task is really establishing

That descoping the live filesystem watcher was correct. `zfs diff` gives the change set deterministically after the
fact, from a snapshot you must take anyway for the oracle. A live daemon would add a second source of truth, a process
that can die mid-run, and an event-ordering problem — in exchange for finer timestamps the experiment does not need.
The cost is that granularity is bounded by snapshot interval, which is exactly the constraint SC-02 exists to expose.

## Steps

1. Snapshot, then in `MNT_PROTECTED` perform one of each: create a file, modify a file, delete a file, rename a file.
   Snapshot again.
2. Run `zfs diff -H <snap1> <snap2>` and confirm all four operations appear with the correct change type
   (`+` added, `-` removed, `M` modified, `R` renamed).
3. Write a small parser producing normalised JSON: `{path, change_type, old_path (for renames)}`. Tab-separated input,
   so this is a dozen lines. Handle paths containing spaces and unusual characters — `zfs diff` escapes them, and a
   naive split will silently mangle such entries.
4. Read the **prior content of the deleted file** from `<mountpoint>/.zfs/snapshot/<snap1>/<path>` and confirm it
   matches what was written, proving AC-4 without any clone or mount.
5. Produce per-snapshot content hashes for the protected subtree (`fs_hashes.tsv`), which the oracle will use as its
   filesystem ground truth. Record how long hashing takes at the lab's data volume — if it is slow it will dominate run
   time and needs bounding.
6. Confirm and record the **granularity consequence**: a change made between two snapshots is only locatable to the
   interval, not the instant. Quantify it for the chosen interval. This becomes SC-02's reported granularity penalty.
7. Confirm `zfs diff` cannot attribute a change to a principal, and record that provenance therefore comes from the
   injector log and workload manifest — which is both simpler and more reliable than inferring it.

## Acceptance tests

| ID | Command | Expected |
| --- | --- | --- |
| T013-1 | `zfs diff -H <s1> <s2>` | all four change types present and correct (AC-5) |
| T013-2 | parser output | valid JSON, four entries, renames carry old path |
| T013-3 | parser fed a path with spaces/newline escapes | handled correctly, not mangled |
| T013-4 | `cat .zfs/snapshot/<s1>/<deleted file>` | original content returned (AC-4) |
| T013-5 | `mount \| grep -c <clone>` | 0 — no clones or loop mounts used |
| T013-6 | `fs_hashes.tsv` | one row per file, stable across repeat runs |
| T013-7 | hashing timing | recorded |
| T013-8 | re-run proof script | same results, idempotent |

## Negative test (required)

Modify a file's content but **not** its size or mtime, and confirm `zfs diff` still reports it as `M`. If it does not,
content hashing rather than diff must carry that detection, and the finding must be recorded explicitly — it would
change how SC-04 (stealthy corruption) is detected, which is the scenario most at risk from this exact behaviour.
