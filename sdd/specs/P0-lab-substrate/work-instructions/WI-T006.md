## Objective

Configure PostgreSQL so that (a) every data change is decodable as JSON to the host, and (b) point-in-time recovery is
possible from a base backup plus archived WAL.

## Keep the two roles separate in your head

| Role | Mechanism | Consumed by |
| --- | --- | --- |
| **Evidence** — what changed, when, before/after | `pg_recvlogical` + `wal2json` -> `db.jsonl` on host | analytics, representations (P3/P5) |
| **Recovery** — restore to a coordinate | base backup + archived WAL (standard PITR) | restore only (P4) |

They are fed by the same WAL but are never interchanged. **Never build analysis on `pg_waldump`** (Article V); it is a
debugging cross-check only.

## Steps

1. Install `wal2json` in the guest if absent (distro package preferred). Record the version.
2. Set in `postgresql.conf`: `wal_level=logical`, `archive_mode=on`,
   `archive_command` pointing at the T005 receiving script writing into `archive/current/`,
   `max_wal_senders` and `max_replication_slots` at least 4, `wal_keep_size` modest,
   `archive_timeout` short enough that idle periods still close segments (record the value chosen and why).
3. Restart the cluster. Confirm `wal_level` and `archive_mode` from `SHOW`.
4. Create the logical slot `SLOT_NAME=lab_slot` with plugin `wal2json`.

   > **Correctness trap:** `wal2json` is consumed via a **replication slot**, not via a `PUBLICATION`. Do not create a
   > publication and expect `wal2json` output; that is the `pgoutput` path. If you find yourself writing
   > `CREATE PUBLICATION` for this task, stop and re-read.

5. Prove the stream: run `pg_recvlogical --start` from the **host** against the guest, writing to a scratch file, make
   a small `INSERT`/`UPDATE`/`DELETE`, and confirm JSON arrives on the host. This exercises the pull architecture (D-2).
6. Confirm archiving works: force a WAL switch, confirm a segment lands in `archive/current/`, and confirm
   `archive_command` failures would be visible (`pg_stat_archiver`).
7. Record `SLOT_NAME`, `SLOT_PLUGIN` and the `wal2json` version in `lab.env` / `observations.md`.

## Acceptance tests

| ID | Command | Expected |
| --- | --- | --- |
| T006-1 | `psql -Atc 'show wal_level'` | `logical` |
| T006-2 | `psql -Atc 'show archive_mode'` | `on` |
| T006-3 | `SELECT slot_name, plugin, slot_type FROM pg_replication_slots` | `lab_slot`, `wal2json`, `logical` |
| T006-4 | host-side `pg_recvlogical` capture during a DML burst | JSON records for insert, update and delete |
| T006-5 | `SELECT pg_switch_wal()` then `ls archive/current` | at least one new segment |
| T006-6 | `SELECT failed_count FROM pg_stat_archiver` | 0 |
| T006-7 | re-run task script | `"changed": false` |

## Negative test (required)

Point `archive_command` at an unwritable path, force a WAL switch, and confirm `pg_stat_archiver.failed_count`
increases and the failure is visible rather than silent. Restore the correct command, confirm recovery to
`failed_count` stable and segments flowing. Capture both states. This proves Article VIII for the archive path.

## Review bundle

Standard five, plus `postgresql.conf.diff`, `recvlogical-sample.jsonl` (a few decoded records),
`archiver-negative-test.log`.

## Operator review checklist

- [ ] Slot is a **logical replication slot** with the `wal2json` plugin, not a publication
- [ ] Decoded JSON was captured **on the host**, proving the pull path
- [ ] A real segment reached `archive/current/`
- [ ] Archive failure is loud and observable
- [ ] `archive_timeout` choice is justified
