# WI-T009 — Isolation test suite with deliberate-regression case

| --- | --- |

## Objective

Turn the out-of-band isolation claim from an assertion into a tested property, and prove the test itself can fail.

## Why the regression case is mandatory

Constitution **Article VIII**: a check that cannot fail is worthless. A suite that passes because it silently probes
the wrong path is worse than no suite, because it produces false confidence that ends up asserted as a result. So
the suite must be shown to go **red** when isolation is genuinely broken, then green again when repaired.

## What must be asserted

For **each** victim principal (`lab_app`, `lab_agent`, and also `postgres`, since it holds the one append path), assert
that the principal **cannot**:

1. read any file under `EVIDENCE_ROOT`
2. list any directory under `EVIDENCE_ROOT`
3. create, modify or delete anything under `EVIDENCE_ROOT`
4. read or list `RESULTS_ROOT`
5. read or list any incident directory under `ARCHIVE_ROOT` other than via the permitted append operation
6. overwrite an existing archived segment
7. reach the host deploy root by any path outside the permitted channel

`postgres` is expected to succeed at exactly one thing: appending a new segment through the T005 channel. Everything
else must fail for it too.

## Steps

1. Write `bin/lab-isolation-test`:
   - runs every assertion above as the relevant principal (via `ssh $VM_SSH sudo -u <principal> ...`);
   - emits JSON: an array of `{principal, assertion, command, expected, observed, result}`, plus a summary count;
   - exits 0 only if every assertion holds; exit 1 on any violation.
2. Implement `--regression`, which:
   - deliberately grants one victim principal read access to a scratch file under `EVIDENCE_ROOT`,
   - re-runs the suite and **requires it to FAIL**,
   - revokes the grant,
   - re-runs and requires PASS,
   - reports all three phases as JSON.
   If the suite does *not* fail in the middle phase, `--regression` exits non-zero: the suite is broken.
3. Make every assertion specific about *why* it failed — permission denied is a pass, but "file not found" is
   **not** a pass, because it may mean the test probed a path that does not exist. Distinguish the two explicitly.
   This is the single most common way an isolation suite silently lies.
4. Record the results as the evidence for the isolation claim.

## Acceptance tests

| ID | Command | Expected |
| --- | --- | --- |
| T009-1 | `bin/lab-isolation-test \| python3 -m json.tool` | valid JSON, all assertions PASS (AC-12) |
| T009-2 | `bin/lab-isolation-test; echo $?` | 0 |
| T009-3 | `bin/lab-isolation-test --regression` | three phases: PASS, FAIL, PASS; exit 0 (AC-13) |
| T009-4 | inspect a passing assertion's `observed` | shows permission denied, not file-not-found |
| T009-5 | as `postgres`: append a new segment through the channel | succeeds (the one permitted action) |
| T009-6 | as `postgres`: list a different incident dir | denied |
| T009-7 | re-run suite | identical results, idempotent |

## Negative test (required)

`--regression` **is** the negative test, and it must be run and captured in full. Additionally, temporarily point one
assertion at a deliberately non-existent path and confirm the suite reports it as an ERROR rather than a PASS. Restore
afterwards.

## Review bundle

Standard five, plus `isolation-results.json`, `regression-three-phase.json`,
`assertion-inventory.md` (every assertion, which FR clause it discharges).

## Operator review checklist

- [ ] Every FR-4.4 clause has at least one assertion
- [ ] All three principals covered, including `postgres`
- [ ] Regression run shows a genuine red-then-green
- [ ] Permission-denied and file-not-found are distinguished
- [ ] `postgres` can append and do nothing else
