## Objective

Build `bin/lab-validate <incident> <restore_of>` that compares the restored sandbox state against the P1 ground-truth
oracle manifest at three levels — row (per-relation row count + content hash), byte (per-file hash), and schema (table
DDL) — and emits per-object mismatches classified `damage_retained` or `legit_lost`, plus integer summary counts.

## Background

The oracle manifest (P1) is the known-good pre-incident state. Validation reads it **only to compare** the restored
state — never to choose the coordinate (ADR-P4-2, Article II scoring role). The restored DB lives in the E002 sandbox
cluster (query it on its own port); the restored files live in the E003 clone mountpoint. A mismatch is
`damage_retained` when the restored state contains damage the optimum eliminated (e.g. a row still deleted, a file
still truncated), and `legit_lost` when the restored state is missing legitimate state the optimum had (coordinate too
early).

## Steps

1. Read `report.partial.json` (E004) for the restore target (sandbox port, clone mountpoint) and the oracle manifest
   path for the incident.
2. **Row level:** for each relation in the manifest, query the sandbox cluster for row count and a deterministic
   content hash (ordered hash of rows), compare to the manifest, and record per-relation match/mismatch.
3. **Byte level:** for each file in the manifest, hash the corresponding file under the clone mountpoint, compare,
   and record match/mismatch including `missing`/`extra`.
4. **Schema level:** dump the restored schema DDL for the managed relations and compare to the manifest DDL; record
   diffs.
5. Classify each mismatch as `damage_retained` or `legit_lost` using the manifest as the optimum reference (never the
   injection log). Compute integer summary counts: `damage_rows_retained`, `legit_rows_lost`, `files_mismatched`,
   `schema_diffs`.
6. Write the validation block into `var/restore/<incident>/<restore_of>/validation.json`. Deterministic: two runs
   byte-identical.

## Negative test (required)

Inject a single known mismatch into the restored sandbox (delete one row that the manifest says should exist, and
truncate one file), re-validate, and confirm: the row shows as `legit_lost` (manifest had it, restored missing it), the
file shows as a byte mismatch, and the summary counts increment correctly. Then inject a retained-damage case (restore
a coordinate that keeps a deleted-by-agent row) and confirm it classifies `damage_retained`. Revert -> clean. This
proves validation is not a rubber stamp and that the two classifications are not swapped.

## Review bundle

Standard five, plus `validation-sample.json`.

## Operator review checklist

- [ ] Row, byte and schema comparisons all run against the oracle manifest
- [ ] Mismatches are classified `damage_retained` vs `legit_lost` correctly (not swapped)
- [ ] Summary integer counts match the per-object mismatches
- [ ] Validation is deterministic across two runs
- [ ] The injected mismatch was caught and correctly classified, then reverted
