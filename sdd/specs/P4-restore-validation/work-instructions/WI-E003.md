# WI-E003 — `bin/lab-restore-fs`: ZFS clone restore of the filesystem subtree

| | |
| --- | --- |
| **Task** | E003 |
| **Phase** | B — The two restore layers |
| **Depends on** | E001 |
| **Blocks** | E004 |
| **Serves** | FR-3, AC-P4-04 |
| **Est.** | 2.5 h |

## Objective

Build `bin/lab-restore-fs <incident> <snapshot>` that reconstructs the protected filesystem subtree by creating a
**`zfs clone`** of the resolved snapshot at a sandbox mountpoint, never rolling back or writing the victim dataset.

## Background

`zfs clone <snapshot> <newdataset>` creates a writable dataset from a snapshot without affecting the origin —
non-destructive. `zfs rollback` destroys everything after the snapshot on the *origin* dataset — destructive, and
prohibited here (ADR-P4-1). The clone is mounted under a sandbox path for validation. The victim dataset
(`labpool/victim/*`) is never rolled back or written.

## Steps

1. Resolve from `etc/lab.env`: the protected dataset name, the sandbox dataset root `labpool/sandbox/<incident>`, the
   sandbox mountpoint. Never guess.
2. Capture the victim dataset's current content hash (and note its `guid`/latest `txg`) **before**.
3. `zfs clone <resolved-snapshot> labpool/sandbox/<incident>/protected`; ensure it mounts at the sandbox mountpoint.
4. Capture the victim dataset content hash **after**; assert byte-identical, and assert the victim dataset's latest
   snapshot list is unchanged (no rollback occurred).
5. Emit `restore_target.fs_clone_dataset`. Idempotent: a re-run detects an existing clone and reports
   `"changed": false`. Provide a teardown path (`zfs destroy` of the **sandbox** clone only) used by E004/E009 and the
   gate; teardown must refuse any dataset name not under `labpool/sandbox/`.

## Acceptance tests

| ID | Tier | Command | Expected |
| --- | --- | --- | --- |
| E003-1 | M | run `bin/lab-restore-fs` for a resolved SC-01 snapshot; inspect `clone.json` | a `zfs clone` exists under `labpool/sandbox/` mounted at the sandbox path (AC-P4-04) |
| E003-2 | M | compare victim dataset hash before vs after; compare snapshot lists | byte-identical; no `zfs rollback` occurred (AC-P4-04) |
| E003-3 | M | grep `commands.log` for `zfs rollback` and for any write to a `labpool/victim` path | none present |
| E003-4 | M | run teardown against a non-`labpool/sandbox` dataset name | refused, non-zero exit |

## Negative test (required)

In a scratch invocation, replace `zfs clone` with `zfs rollback` of the victim dataset and confirm E003-2/E003-3 catch
it (victim hash changes / `zfs rollback` appears in the log) — proving the safety check discriminates. Revert to
`zfs clone` -> passes and the victim is untouched.

## Review bundle

Standard five, plus `clone.json`, `victim-untouched.txt`.

## Operator review checklist

- [ ] Restore produced a `zfs clone` under `labpool/sandbox/`, mounted for validation
- [ ] Victim dataset byte-identical before and after; snapshot list unchanged
- [ ] No `zfs rollback` and no write to a victim path in the command log
- [ ] Teardown refuses any non-sandbox dataset
- [ ] The rollback negative was caught, then reverted to clone
