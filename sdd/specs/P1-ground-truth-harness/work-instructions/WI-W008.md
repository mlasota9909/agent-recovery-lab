## Objective

Build the two-phase harness — `bin/lab-generate-incident` and `bin/lab-evaluate-arm` — plus the analysis and restore
stubs, and prove the whole instrument end to end with a **null run**.

## The property this task exists to establish

ADR-P1-2. An incident is a durable, addressable artefact. Arms are evaluated **against** it, repeatedly, over
byte-identical evidence. If each arm regenerated its own incident, the arms would differ by more than the
representation and the entire ablation would be confounded.

AC-P1-17 is the assertion that proves the property holds, and it is the most important test in the tranche.

## Steps

### Phase 1 — `bin/lab-generate-incident --scenario SC-01`

Seven ordered steps, each evidenced in `commands.log`:

1. Reset (`t0` for a first run of a scenario, `t1` otherwise). **Stop PostgreSQL first** per the P0.1 guard; confirm the
   cluster is back up afterwards.
2. `bin/lab-barrier` — wait for consumer catch-up. Never proceed on a degraded slot.
3. Allocate the incident (`bin/lab-incident --new`), capture the **open coordinate**.
4. Start `bin/lab-workload`; let the quiescent baseline window elapse.
5. `bin/lab-snapshot --label pre_injection`.
6. `bin/lab-inject --scenario SC-01`, then `--verify-timing`. **Fail the whole generation** if the timing window is not
   satisfied — a trivially-easy incident must not enter the dataset.
7. Stop the workload, stop capture, `bin/lab-snapshot --label post_capture`, capture the **close coordinate**, close the
   incident (`bin/lab-incident --close`).

Then: run `bin/lab-ledger-verify` and **refuse to register the incident** if it fails. Run `bin/lab-oracle`. Write
`incident.json` with open/close coordinates, snapshot names, workload rate and mix, and the oracle coordinate. Print the
incident record as JSON.

### Phase 2 — `bin/lab-evaluate-arm --incident <id> --arm stub --tier t2`

1. Reset to the requested tier, then barrier.
2. `bin/lab-ledger-verify`; **refuse to proceed** on failure (AC-P1-18), and record the outcome as
   `ledger_integrity_ok`.
3. Run the analysis component (stub in P1) against the **analysis view**, timing it.
4. Run restore/validate (stub in P1).
5. Read the oracle coordinate from `oracle.json`, compute coordinate-error fields, and append exactly one results row
   via `bin/lab-results append`.
6. Print the run record as JSON. Must be re-runnable any number of times against the same incident.

### The two views (ADR-P1-3)

Materialise two views over the ledger: `scoring` **with** provenance, consumed only by the oracle; `analysis`
**without** provenance (`session_user`, `usename`, originating UID and any equivalent), consumed by the analysis
component. The analysis component must receive only the analysis view. This is enforced by test, not by comment.

### The stubs (ADR-P1-8, FR-6)

- `bin/lab-analyse-stub` implements the interface P3's ranker will implement: takes an incident and the analysis view,
  returns a coordinate plus a `strategy` label. Its declared trivial strategy is **the last snapshot at or before the
  incident close coordinate**. It performs no anomaly scoring, no candidate ranking, no burst analysis.
- `bin/lab-restore-stub` implements the interface P4 will implement and returns verdict `stub`. **No code path in P1
  may emit `correct`** — Article VIII forbids a success that was not earned.

## Negative test (required)

**The provenance leak.** This is the test that protects the validity of the whole experiment. Deliberately wire the
analysis view to include `usename`, and modify the stub to prefer the last coordinate before any `lab_agent` change.
Show that its selected coordinate now **changes** — demonstrating the leak is detectable. Then revert both, and confirm
W008-7 passes again with the coordinate unchanged.

Record this clearly. P3, P5 and P6 inherit this test, so a future leak breaks a pre-existing assertion rather than
quietly producing excellent-looking results.

- [ ] All seven generation steps present and in order, PostgreSQL stopped before reset
- [ ] Timing-window failure aborts generation with no incident registered
- [ ] Ledger-verify failure blocks arm evaluation with no row appended
- [ ] **Three ground-truth coordinates byte-identical across three arm evaluations**
- [ ] Provenance leak demonstrably changes the stub's choice, then reverts
- [ ] No code path can emit `restore_verdict: correct` in P1
- [ ] Stub strategy is the declared trivial one, with no analysis logic smuggled in
