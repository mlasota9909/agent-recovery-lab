## Objective

Build `bin/lab-workload`: the concurrent legitimate activity that makes the research problem real, running as
`lab_app`, recording every commit it makes with its LSN.

## Why the workload is mandatory, not decorative

If the only activity in the incident window is the attack, locating the recovery point is trivial — restore to just
before the single burst. The research problem **only exists** because the engine must separate agent damage from
legitimate concurrent work and choose the coordinate that maximises retained good work while eliminating the damage.

The manifest this task produces is what makes "legitimate rows lost" an exact computation rather than an estimate.

## Steps

1. Seed state. Create the SC-01 baseline: an `orders` relation seeded with a known row count (default 50,000) plus the
   related relations the mix touches. Capture a content manifest (row count and per-row hash) on the clean snapshot.
   Record the seed count in `lab.env` as `SC01_SEED_ROWS`.
2. `bin/lab-workload start|stop|status`:
   - runs as **`lab_app`**, using the `lab_app` database role, so provenance is recorded as a fact by the capture layer
     rather than inferred;
   - issues a mix of inserts, updates and deletes against `orders` and related relations at a configured rate;
   - default mix `insert:60,update:30,delete:10`, default rate 20 tps; both recorded per incident;
   - **legitimate deletes are part of the mix and this is deliberate** — it is what stops "any delete" from being the
     detection signal.
3. Commit manifest. For every committed transaction append one line to
   `${EVIDENCE_ROOT}/<scenario>/<incident>/workload-manifest.jsonl` carrying: commit LSN, commit wall clock,
   operation, relation, affected row identifiers, and row count. The manifest must be sufficient for W007 to compute
   exactly which legitimate rows exist at any candidate coordinate.
4. Obtain the commit LSN authoritatively (`pg_current_wal_lsn()` immediately post-commit, or the value returned by the
   commit path). Do not estimate it from wall clock.
5. The workload must be **rate-stable**: report achieved tps versus configured tps, and fail loudly if achieved rate
   deviates beyond a stated tolerance, because an unstable baseline contaminates the anomaly scoring P3 depends on.
6. Do not implement any damage. The injector is W006. `lab-workload` must have no code path that performs a bulk
   delete.

## Acceptance tests

| ID | Tier | Command | Expected |
| --- | --- | --- | --- |
| W005-1 | M | seed, then `SELECT count(*) FROM orders` | equals `SC01_SEED_ROWS` |
| W005-2 | M | run 60 s, count manifest lines vs committed transactions in the database | exactly equal (AC-P1-08) |
| W005-3 | M | every manifest line has a valid `X/YYYYYYYY` LSN | all lines valid |
| W005-4 | M | manifest LSNs are non-decreasing | true |

| W005-6 | M | achieved tps vs configured | within stated tolerance; deviation fails loudly |
| W005-7 | M | mix proportions over a 60 s run | within tolerance of `insert:60,update:30,delete:10` |
| W005-8 | M | grep `bin/lab-workload` for unqualified bulk delete patterns | none |
| W005-9 | M | `stop` then `status` | reports stopped; no orphan processes |
| W005-10 | M | re-run `start` when already running | `"changed": false`, no second writer |

## Negative test (required)

**Manifest completeness under stop.** Kill the workload abruptly mid-run (not a graceful stop) and assert that the
manifest contains **no line for a transaction that did not commit**, and no missing line for one that did. Compare
against the database. A manifest that records intent rather than commits would make "legitimate rows lost" wrong in
every subsequent run, and it would be wrong in the flattering direction.
