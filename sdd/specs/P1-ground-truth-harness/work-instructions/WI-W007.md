## Objective

Build `bin/lab-oracle`: compute the **known-optimal recovery coordinate** for an incident, plus the manifest that makes
outcome error an exact computation. This is the reference every arm in the project is scored against.

## Why this is the most consequential component in the tranche

This task answers two methodological gaps directly: how "correct" recovery is adjudicated, and scoring that rests on a
single reviewer's judgement. Because the incident is **scripted**, the optimum is
not a matter of opinion — it is computable. Replacing an author-assigned ordinal score with an objective distance is
the single biggest methodological upgrade in the experiment.

That also means a subtly wrong oracle would silently corrupt every result in the project while looking entirely
plausible. Hence the independent cross-check in the acceptance tests.

## Definition for SC-01

The optimum is the **commit LSN of the last legitimate transaction before the malicious DELETE**. Restoring there
retains all legitimate work committed up to that point and removes the deletion entirely.

Computed from:
- `injection.json` → the malicious commit LSN;
- `workload-manifest.jsonl` → all legitimate commit LSNs;
- `snapshots.json` → the snapshot at or below, per the frozen coordinate contract.

The optimum is then resolved into a full coordinate triple by `bin/lab-coordinate`, so `snapshot`, `skew_ms` and
`skew_bytes` are populated by the P0 resolver rather than recomputed here. Do not reimplement resolution.

## Steps

1. `bin/lab-oracle --incident <id>`:
   - reads `injection.json` and `workload-manifest.jsonl`;
   - selects the greatest legitimate commit LSN strictly less than the malicious commit LSN, using **numeric** LSN
     comparison via `lib/lsn.py`;
   - resolves it to a coordinate triple by invoking `bin/lab-coordinate --lsn <that LSN>`;
   - writes `oracle.json` containing the coordinate, plus an `inputs` block recording every file read with its SHA-256
     and the specific records used, so a reader can audit how the optimum was derived (FR-3.6);
   - prints the coordinate as JSON.
2. **Provenance permission.** The oracle **may** read provenance fields — it is the only component permitted to do so
   (Article II, ADR-P1-3). State this explicitly in a header comment so a future reader does not "fix" it. Every other
   component reads the analysis view.
3. `oracle-manifest.json` for outcome scoring, containing:
   - the set of legitimate rows committed at or before the optimum, sufficient to compute `legit_rows_lost` exactly;
   - the set of rows the injection destroyed, sufficient to compute `damage_rows_retained` exactly;
   - byte sizes for both, so the `_bytes` fields are exact rather than derived from row counts.
4. **Determinism.** Recomputing over the same frozen incident must produce a **byte-identical** coordinate. Sort
   deterministically, canonicalise JSON with sorted keys, and never embed a timestamp of computation inside the
   coordinate object. If you need a computed-at timestamp, put it outside the coordinate, in the `inputs` block.
5. **Fail loud (FR-3.5).** Exit non-zero, naming the precondition, if: `injection.json` is absent or malformed; the
   manifest is absent or empty; no legitimate commit precedes the injection; the manifest and ledger disagree; or no
   snapshot exists at or below the optimum. Never guess, never fall back to the nearest available value.
6. Do **not** implement candidate generation, ranking, anomaly scoring or any analysis. The oracle knows the answer
   because the incident was scripted; it does not detect anything.

## Negative test (required)

**Off-by-one in the wrong direction.** Construct a variant that selects the greatest legitimate commit LSN *less than
or equal to* the malicious commit, instead of strictly less than, and demonstrate that this variant would select a
coordinate that **retains the damage**. Show the resulting `damage_rows_retained > 0` against the manifest, then
confirm the shipped implementation selects strictly less than and retains zero damage.

This is the single most dangerous class of bug in the project: a coordinate one transaction too late looks correct by
every timing measure and silently preserves the thing you were recovering from. Prove the boundary is right.
